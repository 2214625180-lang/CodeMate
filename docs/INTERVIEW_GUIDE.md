# CodeMate Interview Guide

本指南包含 **60 个问题，10 个主题**，参照 KnowledgeFlow 面试指南的组织方式，围绕当前 CodeMate 源码准备项目讲解。每题依次提供「30 秒回答」「深挖回答」「可能追问」「容易答错的点」。先练习短回答，再用调用链、执行证据和取舍回答追问。

**项目范围：** 面向中小型 TypeScript / JavaScript / Python 仓库、覆盖少量 Vue fixture 的可验证代码修复 Agent。主线是失败复现、可引用代码证据、受控工具决策、隔离补丁验证与持久化评测；代码问答和 MCP 是相关能力。当前不把它描述为能修复任意仓库的通用自治开发者，也不把托管执行平面的配置和部署工件描述为已通过生产验收。

阅读入口：[README](../README.md) · [Demo](demo-script.md) · [代码阅读指南](code-reading-and-agent-learning-guide.md) · [能力与证据边界](capability-matrix.md)。本文按当前工作区源码核对；默认值来自配置，测量值来自明确标注的历史 artifact，均不代表最佳参数或真实模型效果承诺。

## A. 项目总览与架构

### 1. 问题：用 1 分钟介绍 CodeMate

#### 30 秒回答

CodeMate 是一个可验证代码修复 Agent。用户提交仓库问题和测试命令后，系统先在隔离工作区复现失败，再由模型选择检索、读文件等受控工具定位问题，生成补丁并运行目标测试与回归测试，最后保存 Diff、执行轨迹和验证结论。

#### 深挖回答

可以按问题、机制、边界展开：模型生成的代码不一定正确，所以需要把修复建议放进可执行验证流程。模型负责提出下一步动作，确定性执行器负责权限、预算和工具调用，验证模块依据原始执行结果决定终态。

只有基线失败、补丁应用成功、修后目标与回归测试均通过，才记为 `verified_success`。当前聚焦有可执行复现方式的局部修复；真实模型修复成功率尚未在已提交 benchmark 结果中发布。

#### 可能追问

最核心的模块是哪一个？如果模型说修好了但没有测试怎么办？项目目前能证明什么？

#### 容易答错的点

把生成 Diff 当成修复成功，或声称支持任意语言、任意仓库和自动合并。

### 2. 问题：为什么做这个项目？

#### 30 秒回答

我想解决代码助手给出建议后，缺少可靠执行证据的问题。项目把定位、修改、验证和记录连起来，让用户能看到改了什么、测试是否真正执行、失败发生在哪个阶段。

#### 深挖回答

只展示一段生成代码，无法说明原问题是否复现，也无法判断是否破坏其他行为。CodeMate 用基线测试建立起点，用目标测试检查修复点，再用回归检查约束影响范围，保留失败和基础设施异常等独立结果。

这是一项工程目标；目前没有用户研究或真实模型对照实验支持“开发效率提高多少”的结论。

#### 可能追问

已有测试能否覆盖业务正确性？为什么从代码修复切入，而不是通用开发需求？

#### 容易答错的点

用没有证据的效率提升百分比作为项目价值证明。

### 3. 问题：和普通代码 RAG 问答有什么区别？

#### 30 秒回答

代码 RAG 主要返回相关代码和解释；CodeMate 的修复流程还会执行动作、修改隔离工作区、验证测试，并根据新失败证据继续调查。检索是修复闭环中的证据来源之一。

#### 深挖回答

`RetrievalService` 负责召回代码；`AgentService` 编排修复；`LocalAgentExecutor` 执行受约束的动作；`SandboxRunner` 应用补丁并运行测试；`verification.py` 计算验证结论。职责分别对应找证据、做决策、执行和判定。

仓库中也有独立的 `ChatService`，但不能把问答流里的自然语言结论直接当成修复验证结果。

#### 可能追问

为什么 Agent 还需要 ReadFile？检索准确是否意味着修复一定成功？

#### 容易答错的点

把有工具名称的问答称为完整修复闭环，或混淆 Retrieval Recall 与 Fix Success Rate。

### 4. 问题：一次修复请求经过哪些模块？

#### 30 秒回答

请求先通过身份与仓库归属检查，保存 AgentRun，再由 RQ Worker 执行 AgentService。服务创建隔离工作区，运行 LangGraph 中的复现、调查、补丁和验证节点，最后保存结果，前端通过 Run API 和 trace 展示进度。

#### 深挖回答

主调用链是 API → `create_fix_run` → 队列 → `run_agent_job` → `run_fix` → `_invoke_fix_graph`。图内从 `InspectRepository`、`ReproduceFailure` 进入受控决策循环，再走 `GeneratePatch`、`ApplyPatch`、`TargetedTests`、`RegressionChecks` 和 `FinalAnswer`。

MCP 启用时还有远程工具、审批与对账分支。Run 是任务身份，Graph State 是可恢复执行状态，AgentStep 是面向用户的轨迹，三者不能互相替代。

#### 可能追问

为什么先提交 Run 再排队？数据库成功但队列失败怎么办？整个任务是一个事务吗？

#### 容易答错的点

声称 HTTP 请求一直同步执行修复，或数据库写入和 Redis 入队天然原子化。

### 5. 问题：为什么采用 Next.js、FastAPI、PostgreSQL、Redis 和 Qdrant？

#### 30 秒回答

它们分别承担交互界面与服务端代理、业务 API、关系数据与持久化状态、任务队列以及向量搜索。核心是职责分工清楚，让耗时修复与请求响应分离。

#### 深挖回答

PostgreSQL 保存仓库、文件、Chunk、Run、Step 和 checkpoint 等数据；Redis / RQ 调度后台工作；Qdrant 提供向量候选；前端展示引用、Diff、测试证据和评测对比。

这些选择带来多个服务的运维和一致性成本，并不意味着单数据库或其他队列无法实现。版本信息应引用实际 manifest，不靠背诵旧文档。

#### 可能追问

为什么不用 PostgreSQL 向量扩展？如果 Redis 停了，哪些能力还可用？

#### 容易答错的点

把技术栈数量当作架构水平，或者声称选型已通过全面性能对比。

### 6. 问题：项目中最能体现工程能力的设计是什么？

#### 30 秒回答

我会重点讲模型决策与执行授权分离，以及成功结论必须来自执行证据。即使模型输出错误、重复动作或提前结束，系统仍由明确规则控制工具与最终结果。

#### 深挖回答

动作通过 Pydantic discriminated union 建模；执行器重复校验、检查预算并记录动作与证据指纹；补丁进入独立应用与验证节点。最终判定函数不依赖模型自评，可以单独测试各种缺失证据和失败组合。

Checkpoint、Timeline 和评测门禁进一步使问题可恢复、可审查、可比较。面试时应选一条实际调用链讲透，并区分设计、代码和运行证据。

#### 可能追问

如何证明模型不能绕过授权？你最担心哪一种假成功？

#### 容易答错的点

只介绍用了某个 Agent 框架，没有说明框架之外的约束和验证逻辑。

## B. 仓库索引与代码分块

### 7. 问题：一个仓库进入系统后经历什么？

#### 30 秒回答

后台索引任务准备 staging checkout，扫描支持的源码，解析文件和语义 Chunk，写关系元数据与向量，切换工作区并提交新索引状态，然后清理旧向量并刷新仓库摘要。

#### 深挖回答

`IndexService` 区分全量和增量索引，记录 commit、文件数、Chunk 数及语言统计。新向量和工作区切换发生在最终数据库提交之前，失败时尝试回滚数据库、删除新向量和恢复旧工作区。

状态会经过 cloning、parsing、embedding，成功后为 indexed；异常会记录 failed。状态名称表达处理阶段，不代表每个中间步骤都已经原子提交。

#### 可能追问

为什么用 staging checkout？向量成功而数据库提交失败怎么办？

#### 容易答错的点

说 clone 完成就等于检索可用，或把三个存储介质描述为一个事务。

### 8. 问题：为什么代码要按 AST / 语义结构分块？

#### 30 秒回答

函数、类、方法和组件是理解代码的重要边界。语义分块能保留符号与行号信息，减少固定字符窗口把函数签名和实现拆开的情况，也便于回答定位到源码。

#### 深挖回答

Python 使用标准库 AST；JS/TS 使用 Tree-sitter 解析并有简化解析回退；Vue 由独立 SFC chunker 处理。Chunk 保存路径、符号名、类型、起止行、正文及导入导出信息。

这种方案需要维护语言适配，且语义单元可能很长。当前 Python chunker 保留完整函数，并未实现超长函数内部的进一步切分。

#### 可能追问

超长类怎么办？类和方法同时入库会不会重复？为什么不用固定窗口加 overlap？

#### 容易答错的点

说 AST 保证每块都很短，或套用另一个项目的固定 Chunk Size 和 overlap 参数。

### 9. 问题：解析失败或者文件没有函数，会发生什么？

#### 30 秒回答

不同语言的失败策略不同。Python 的语法错误会返回空 Chunk 结果；JS/TS 在解析器调用异常时使用简化解析回退。文件存在于仓库中不代表它一定形成可检索的语义 Chunk。

#### 深挖回答

Python chunker 主要遍历顶层函数、类及类方法，普通顶层赋值不一定形成独立 Chunk。索引扫描和语义分块是两个阶段，应分别看文件记录与 Chunk 数量。

Agent 的 ListFiles、ReadFile 可以补充检索之外的调查，但读到文件不等于解析器支持其语言。若要升级解析覆盖，需要增加明确样例和回归验证。

#### 可能追问

解析失败为什么不直接终止全仓库索引？回退结果的质量怎么判断？

#### 容易答错的点

承诺每个文件都能被向量检索，或认为所有解析错误都有相同回退策略。

### 10. 问题：增量索引怎么判断哪些文件变了？

#### 30 秒回答

系统更新 staging checkout 后重新扫描源码，把路径集合和内容哈希与现有文件记录比较。新增或内容变化的文件重新写 Chunk 与向量，删除的文件移除旧索引，未变化文件复用已有记录。

#### 深挖回答

`_index_incremental` 使用 `content_hash` 判断变化，按 deleted paths 和 changed paths 替换相关数据。新数据库视图提交之后才清理被替代的旧向量。

这里的“增量”主要减少重建与 embedding，不意味着完全不扫描、不解析未改文件。也不能把按内容哈希更新直接说成 AST 节点级增量分析。

#### 可能追问

重命名如何处理？Embedding 模型变化但源码不变时会怎样？同一仓库并发索引安全吗？

#### 容易答错的点

说只读取 Git diff 就完成索引，或宣称已有完整并发索引隔离机制。

### 11. 问题：PostgreSQL、Qdrant 和文件系统如何保持一致？

#### 30 秒回答

采用提交顺序与补偿机制：保留旧外部状态，写新向量、切换工作区并提交数据库，失败时回滚和恢复，提交后再清理旧数据。它能处理部分失败，但不是跨系统强事务。

#### 深挖回答

`IndexService` 跟踪新旧 point ID 和备份工作区，尽量避免新索引失败时破坏旧数据。向量检索还会用 Chunk ID 回查当前数据库记录，过滤数据库中已不存在的命中。

突然崩溃、清理失败、提交结果不确定和并发执行仍需要单独分析。现有 best-effort 清理不能表述为完整的后台自动对账系统。

#### 可能追问

为什么不用 outbox？如果进程在工作区切换后退出怎么办？如何识别孤立向量？

#### 容易答错的点

把数据库 rollback 说成能撤销 Qdrant 和目录操作，或把过滤孤立命中说成已清理孤立数据。

### 12. 问题：Repo Memory 和另一个项目的长期记忆有什么区别？

#### 30 秒回答

CodeMate 的 Repo Memory 是仓库结构、依赖、关键文件和符号的摘要，用来给 Agent 提供项目背景；它不是用户偏好记忆，也不是每轮聊天自动学习形成的长期记忆。

#### 深挖回答

`RepoMemoryService` 从 Repository、CodeFile、CodeChunk 和仓库配置文件整理结构化数据与摘要，保存到仓库记录中。索引结束后会尝试刷新，Agent 在初始化背景时读取。

它有符号数量等上限，而且可能随仓库变化而过期。精确定位仍依赖检索和读取源码，不能让摘要代替当次证据。

#### 可能追问

摘要需要 LLM 生成吗？什么时候刷新？摘要与实际文件不一致时信谁？

#### 容易答错的点

把 Repo Memory 说成自动提取用户事实的向量记忆，或声称摘要完整覆盖仓库。

## C. Embedding、Hybrid Retrieval 与 Citation

### 13. 问题：为什么既需要关键词检索又需要向量检索？

#### 30 秒回答

代码问题往往同时包含精确的符号、路径、异常名和自然语言描述。关键词适合匹配明确标识符，向量负责补充语义相关候选，混合召回让两种信号共同参与排序。

#### 深挖回答

`RetrievalService` 在 hybrid 模式下分别生成关键词和向量候选。PostgreSQL 使用全文检索；非 PostgreSQL 环境有 ILIKE 回退。向量候选先经过最低分过滤，再与关键词结果做 RRF 融合。

这解释了设计动机，但不能从 mock embedding 的 smoke 结果推导真实模型下的收益，仍需要固定数据集对照。

#### 可能追问

关键词检索是 BM25 吗？全是中文问题怎么办？向量服务失败还能回答吗？

#### 容易答错的点

把 PostgreSQL 全文检索直接称为 BM25，或说 hybrid 必然在所有任务上更好。

### 14. 问题：两路检索分数不同，怎么融合？

#### 30 秒回答

系统使用 Reciprocal Rank Fusion，按结果在各路中的名次累加分数，避免直接相加量纲不同的全文检索分和向量相似度。当前公式是每路贡献 `1 / (60 + rank)`。

#### 深挖回答

结果以 Chunk ID 合并，同一路重复 ID 不重复计分，两路都命中则标记 hybrid。排序相同时再用 Chunk ID 提供确定顺序，便于测试和结果复现。

RRF 只融合已召回的候选，不能找回两路都没召回的内容，也不保留原始分数差距所表达的全部信息。

#### 可能追问

为什么常数是 60？为什么不用分数归一化？候选池大小会影响结果吗？

#### 容易答错的点

套用另一个项目的 similarity 与 importance 加权公式，或把 RRF 分数解释成概率。

### 15. 问题：Query Rewrite 和 Rerank 是由模型完成的吗？

#### 30 秒回答

当前两者主要是确定性规则。Query Rewrite 提取路径、符号、异常名，并补充有限的中文词汇映射；Rerank 根据初始分数、关键词覆盖、路径和符号匹配等信号调整排序。

#### 深挖回答

`rewrite_query` 使用正则和固定映射；`_rerank_score` 对精确路径、精确符号、错误名等设置不同加分。它不调用 Cross-Encoder，也不是 LLM 对候选逐条打分。

优点是容易复现、低额外依赖，代价是规则可能偏向某些问题表达。参数和规则是否有效，应由消融与错误样本分析验证。

#### 可能追问

中文映射没覆盖的业务词怎么办？为什么路径匹配权重较高？如何接入学习型重排？

#### 容易答错的点

说用了一个训练过的 reranker，或声称查询重写能理解任意领域术语。

### 16. 问题：Top K、阈值和上下文扩展分别在哪里生效？

#### 30 秒回答

默认 Top K 为 8，候选倍数为 4，向量最低分为 0.72。先扩大召回、过滤向量候选、融合和重排，再选 Top K；之后可添加同文件的相邻或父级 Chunk。

#### 深挖回答

默认上下文窗口为 1，最多额外加入 4 个 Chunk；扩展结果按 Chunk ID 去重，分数取对应命中的 0.65 倍。因此最终结果数量可能超过 Top K，0.72 也不是作用于最终 rerank 分数的阈值。

这些是当前配置和规则，不是实验确定的最优参数。扩展能补充上下文，也可能增加无关内容和输入开销。

#### 可能追问

为什么不是所有结果都扩展？扩展后是否有统一 token 硬预算？阈值怎么校准？

#### 容易答错的点

把 Top K 说成扩展后的绝对数量上限，或把分数阈值套到所有检索阶段。

### 17. 问题：Embedding 编码什么？替换模型有什么影响？

#### 30 秒回答

索引输入包含代码正文和路径、语言、符号、导入导出等元数据；查询输入包含原问题和提取出的检索线索。Embedding Provider 与生成模型分开配置，替换向量模型需要重新核对索引兼容性。

#### 深挖回答

`build_code_embedding_text` 和 `build_query_embedding_text` 负责构造文本；工厂支持 mock、openai 与 openai-compatible 适配。这里应讲仓库适配能力，不把供应商接口实现细节当成检索质量证明。

不同 embedding 模型即使维度相同，也不保证语义空间一致。升级时应明确模型、维度和索引版本，重新构建需要迁移的向量并重跑评测；仅换生成模型通常不改变已有向量空间。

#### 可能追问

为什么把路径加入 embedding？模型变化但内容哈希不变怎么办？Mock 能测什么？

#### 容易答错的点

说 CodeMate 与参考项目一样使用 BGE-M3，或认为维度一致就可以混用新旧向量。

### 18. 问题：Citation 怎么避免由模型随意编造？

#### 30 秒回答

结构化 Citation 由后端根据真实检索 Chunk 生成，包含仓库、路径、符号和行号。它与提供给模型的检索结果有明确关联，但不能证明答案每句话都被证据支持。

#### 深挖回答

`ChatService` 把检索结果转换为 `LLMContext`，生成 token 后再发送 citation。单仓库取结果前 5 条，多仓库取前 8 条，因此引用列表不一定列出全部输入上下文。

这些行号属于索引版本，源码变化后需要考虑定位时效性。结构化引用的可信来源与模型正文里的事实正确性，是两种不同保证。

#### 可能追问

为什么模型上下文比引用多？能否逐句绑定引用？跨仓库相同文件名怎么区分？

#### 容易答错的点

说引用保证零幻觉，或照搬参考项目“所有最终上下文都持久化为 Sources”的实现。

## D. Controlled Agent Loop

### 19. 问题：这个 Agent 的自主性体现在哪里？

#### 30 秒回答

模型根据当前问题、假设、证据和工具观察选择下一步动作，例如先查符号、再读文件、运行诊断测试或请求生成补丁。具体调查路径可以变化，但可用工具与执行限制由系统固定。

#### 深挖回答

`PlanNextAction` 每轮返回一个动作，`ExecuteLocalAction` 产生 observation 后再次规划。修复外围仍有确定性的复现、应用和验证节点，所以它结合了动态调查与固定验证流程。

仓库还保留 fixed workflow 模式用于 planner 消融；固定模式与自适应模式的差异需要真实评测，不能靠节点图推导效果提升。

#### 可能追问

和固定 workflow 的区别是什么？为什么只允许一次选一个动作？

#### 容易答错的点

把所有步骤都说成模型自由决定，或只因为用了 LangGraph 就声称具备自主规划。

### 20. 问题：为什么动作使用 Pydantic discriminated union？

#### 30 秒回答

不同动作具有不同参数约束，用 action 字段区分有限类型，可以让未知动作、额外字段和越界参数在执行前被拒绝。模型输出因此是受约束的请求对象。

#### 深挖回答

`actions.py` 定义 SearchCode、ReadFile、ListFiles、符号与图导航、RunTests、GeneratePatch、Finish 等类型，公共配置包含 `extra="forbid"`。例如 ReadFile 校验行号顺序，图导航限制方向与深度。

Provider 解析后，执行器还用同一个适配器再次校验。Schema 约束结构，路径权限和测试命令许可仍需执行层单独检查。

#### 可能追问

为什么不能让模型直接输出 shell？Schema 校验通过就安全吗？新增工具要改哪里？

#### 容易答错的点

把 JSON 合法等同于业务合法，或认为模型声称工具安全即可执行。

### 21. 问题：怎么防止 Agent 无限循环和重复工具调用？

#### 30 秒回答

系统同时限制规划次数、工具次数、token、时间和连续无进展次数，并记录动作与证据指纹。重复请求、新证据不足和被规则拒绝的动作都会受到控制，达到边界就结束调查。

#### 深挖回答

动作指纹基于排序后的执行参数计算，排除 hypothesis 和 rationale，避免模型只换解释文字就把同一调用伪装成新动作。结果证据和补丁也有各自指纹。

当前默认本地工具 12 次、planner 16 次、planner token 24000、Loop 600 秒、连续无进展 3 次。指纹处理的是确定性重复，不能识别所有语义等价查询。

#### 可能追问

相同查询在仓库状态变化后是否还该拒绝？什么叫新证据？怎样避免误停机？

#### 容易答错的点

只靠 Prompt 中“不要重复”控制循环，或把 hash 去重描述成语义理解。

### 22. 问题：有 token 和时间预算就能保证总成本与耗时吗？

#### 30 秒回答

不能直接这样承诺。当前 planner token 计数约束的是规划调用，时间检查也发生在具体控制点；整次任务还包含补丁生成、embedding、沙箱测试与排队等开销。

#### 深挖回答

`AgentService` 在规划前检查预算，调用后累加返回 token，用量超过限制时转换为受控 Finish。本次调用已经消耗的 token 无法撤回，某些统计还需要区分 Provider usage 与估算。

沙箱 timeout 和 RQ job timeout 另有配置。若要保证全流程成本，需要把所有模型调用、测试阶段及取消机制纳入统一设计，不能把单个计数器扩大解释。

#### 可能追问

某次调用直接超过剩余预算怎么办？Provider 卡住时由哪一层终止？

#### 容易答错的点

说 24000 是整次修复的精确总 token 上限，或 600 秒包含排队和全部工作。

### 23. 问题：FindReferences 和 GetCallGraph 能解析真实调用关系吗？

#### 30 秒回答

它们提供基于索引元数据和标识符匹配的静态导航候选，帮助缩小调查范围。当前不是编译器级名称解析，不能保证别名、动态分派、重载或重新导出的调用边正确。

#### 深挖回答

工具契约和能力矩阵明确标注这一边界。Agent 获得关系候选后仍应读取源码，并结合失败测试验证其是否与问题相关。

图导航具有方向和深度限制，适合局部代码理解。若升级到精确符号关系，需要语言服务或编译信息，也要付出构建环境和语言适配成本。

#### 可能追问

同名函数怎么区分？动态 import 怎么处理？为什么暂时不用 LSP？

#### 容易答错的点

把 GetCallGraph 的名称当作完整静态分析能力证明，或声称已实现知识图谱推理。

### 24. 问题：检索没有结果，或者模型决定 Finish，怎么办？

#### 30 秒回答

检索为空不会自动变成成功或失败修复，Agent 可以继续用文件列表、符号查找和读取补充证据；持续无进展会触发停机。Finish 只请求结束流程，成功与否仍由验证模块判定。

#### 深挖回答

向量召回异常在当前实现中会返回空列表，hybrid 模式仍可利用关键词候选；vector-only 则可能没有结果。检索服务异常、索引覆盖不足和代码确实不相关，不能混为同一种质量结论。

`LocalAgentExecutor` 把 Finish 路由到 final，`build_verification_result` 再检查基线、补丁和测试。模型的 reason 不具有修改验证状态的权力。

#### 可能追问

空结果应该暴露降级信息吗？Finish 没有补丁时是什么状态？如何区分漏召回与没有相关代码？

#### 容易答错的点

把降级当成服务健康，或认为模型返回 Finish 就表示任务成功。

## E. 补丁生成与严格验证

### 25. 问题：为什么一定要先运行修复前的测试？

#### 30 秒回答

先运行基线才能证明原问题在当前环境中存在。否则修后测试通过，可能只是原本就通过，无法证明补丁修复了问题。

#### 深挖回答

`ReproduceFailure` 先于补丁生成。基线通过会直接进入 final 并得到 `not_reproduced`；基础设施错误也停止继续修复。缺失或跳过基线不能建立可信起点，即使之后有补丁也不能判定 verified success。

失败复现本身还依赖测试是否对应用户问题。如果用户给了无关失败测试，仅有退出码变化仍不足以证明满足原始需求。

#### 可能追问

没有测试命令还能生成补丁吗？偶发失败如何处理？如何确认复现针对的是原问题？

#### 容易答错的点

说修后通过就能证明修复，或声称当前已自动解决 flaky test。

### 26. 问题：verified_success 的精确条件是什么？

#### 30 秒回答

基线必须被分类为测试失败，补丁应用成功，目标测试与回归测试必须都被分类为通过。测试通过要求真实执行、通过标记和零退出码一致，不能只看模型总结或一个 passed 字段。

#### 深挖回答

`classify_test_result` 先区分 infrastructure、skipped、test_failure 等信息，再解释 `tests_ran`、`passed` 和 `exit_code`。`build_verification_result` 按生命周期组合这些结果，最终持久化阶段还会核对成功证据完整性。

这个结论表达“当前执行证据符合验证契约”，不等于所有业务行为被证明正确。测试覆盖率、命令可信度和环境一致性仍决定保证的实际范围。

#### 可能追问

exit_code 为 0 但 tests_ran 为 false 呢？验证字段互相矛盾时谁优先？

#### 容易答错的点

把 verified_success 理解为代码绝对正确，或让前端、模型自行设置成功状态。

### 27. 问题：为什么要区分五种修复终态？

#### 30 秒回答

不同状态代表不同处理方向：verified_success 有完整通过证据；unverified_patch 有补丁但验证证据不足；not_reproduced 表示基线已通过；failed 表示补丁或测试失败；infra_error 表示执行基础设施妨碍验证。

#### 深挖回答

例如，未检测到测试命令时 `tests_ran=false`，即使返回码是 0 也不能算通过；容器或依赖异常不能被记为模型修复失败后继续盲目改代码。UI、Run 持久化和 benchmark 都需要保留这个区别。

判定规则有优先级：基线的基础设施错误或已经通过会先决定结果，后续数据不能补偿缺失的可信起点。

#### 可能追问

有补丁但回归测试未运行是什么状态？为什么不全部用 success / error？

#### 容易答错的点

把跳过测试算成功，或把部署故障与业务测试失败合并成同一修复指标。

### 28. 问题：目标测试和回归测试有什么区别？

#### 30 秒回答

目标测试检查当前修复点，回归测试检查更广的既有行为。系统在目标测试通过后才进入回归阶段，避免一个局部修复破坏相关功能而仍被宣布成功。

#### 深挖回答

`inspect_repository` 同时记录用户请求或解析出的测试命令，以及仓库检测到的回归命令。回归优先使用检测到的仓库测试命令，缺少独立命令时可能回退为目标命令。

因此有两个验证阶段，不意味着它们总是两个独立测试集合。Demo 的购物车与结算逻辑展示了局部测试通过而完整回归可能失败的场景，但不会强制真实模型第一轮必须失败。

#### 可能追问

两个命令相同还有多少额外价值？怎么选择回归范围？测试太慢怎么办？

#### 容易答错的点

声称当前自动生成了完整回归测试，或把两个阶段误说成必然两套不同测试。

### 29. 问题：补丁生成为什么还要显式读取文件？

#### 30 秒回答

检索适合找候选位置，生成可应用补丁还需要具体文件内容。当前状态中的 files 保存显式 ReadFile 结果，补丁生成器结合这些内容、诊断和失败证据提出修改。

#### 深挖回答

`generate_patch` 优先把修后回归或目标失败作为新的失败上下文，再考虑诊断或基线结果。生成的 diff 先计算指纹，完全相同的补丁不会再次进入应用阶段。

补丁由 `git apply` 在临时工作区处理；文本看起来合理不代表能应用。ReadFile 有行数限制，因此也不能假设一次读取就取得整个大文件。

#### 可能追问

检索的旧代码与工作区不同怎么办？补丁上下文不匹配时如何处理？新文件能出现在最终 Diff 吗？

#### 容易答错的点

说模型直接修改原始仓库，或把生成一段 diff 当成 git apply 已成功。

### 30. 问题：Reflect 失败反思具体做什么？

#### 30 秒回答

Reflect 保存本次测试失败的阶段、命令和错误证据，重置当前临时工作区，再让 planner 选择新的调查路径。它帮助后续决策使用真实失败反馈。

#### 深挖回答

当前 reflect 节点主要做确定性的证据整理、指纹去重与状态更新，并非一个独立“反思专家 Agent”。重置可以避免下一轮补丁叠加在已失败修改上，已有失败轨迹仍保留供审查。

重试受最大修复迭代、工具和 planner 预算共同约束。失败反馈可能改善决策，但没有已发布的真实模型实验能证明必然提高成功率。

#### 可能追问

为什么不在上轮补丁上继续改？失败证据会不会丢失？同一个补丁换了文本格式还能被识别吗？

#### 容易答错的点

把 Reflect 描述成模型自我训练，或声称无限反思最终总能修好。

## F. 沙箱与执行边界

### 31. 问题：为什么每次修复需要独立 workspace？

#### 30 秒回答

Agent 会修改文件并执行仓库代码，独立工作区可以把试错修改与索引源仓库分开，也便于失败后重置和任务结束后清理。

#### 深挖回答

`SandboxRunner.create_workspace` 从索引仓库创建临时副本，排除敏感文件、依赖与构建目录等，Agent 工具围绕这个 workspace 工作。`_invoke_fix_graph` 在 finally 中清理工作区。

隔离副本仍然需要路径校验、容器执行和资源限制配合。独立目录本身不能隔离恶意代码的进程权限和网络访问。

#### 可能追问

为什么不直接在用户 checkout 上改？并发运行怎么互不影响？进程突然退出会留下什么？

#### 容易答错的点

把临时目录叫作完整安全沙箱，或保证 finally 能处理所有进程崩溃。

### 32. 问题：测试命令白名单为什么还要在执行前检查？

#### 30 秒回答

模型或上层服务提供的命令仍是不可信输入，最终执行层必须独立确认它与允许命令精确匹配，避免通过替代调用路径绕过限制。

#### 深挖回答

`SandboxRunner._run_tests` 再次检查 `settings.allowed_test_commands`，不在白名单的命令返回未执行的错误结果。底层会构造容器内 shell 命令，因此不能因为外层调用使用参数数组就说完全没有 shell 风险。

即使允许 npm test，仓库里的 test script 仍可以运行任意代码；白名单限制入口，容器与网络策略才继续约束这些代码的能力。

#### 可能追问

命令后追加分号能通过吗？允许 pytest 是否就安全？依赖安装脚本如何约束？

#### 容易答错的点

把白名单当作对测试代码的安全审查，或说系统完全不用 shell。

### 33. 问题：Docker 测试沙箱有哪些限制？

#### 30 秒回答

当前本地 Docker 路径使用独立测试容器，设置内存、CPU 和执行超时，默认关闭网络，并只把任务工作区挂载进去。它适合本地验证，但不能直接当作已验收的恶意多租户隔离环境。

#### 深挖回答

本地命令中内存为 512 MiB、CPU 为 1，默认沙箱 timeout 为 120 秒，网络禁用时使用 `--network none`。这些限制约束资源和联网能力，不构成内核隔离漏洞不存在的证明。

仓库有 gVisor、Firecracker 等配置或控制路径，但更强运行时和托管部署的证据要单独核对，不能从枚举值推导部署已经成功。

#### 可能追问

容器和 microVM 的威胁边界有何不同？测试超时属于业务失败吗？

#### 容易答错的点

把 Docker 等同于虚拟机，或虚构当前命令包含未配置的安全选项。

### 34. 问题：默认禁网时，项目依赖怎么安装？

#### 30 秒回答

禁网测试要求依赖已经可用，或者 fixture 无需额外安装。当前检测到需要安装依赖但 Docker / gVisor 禁网时，会返回跳过执行的结果，不能把这次运行记为通过。

#### 深挖回答

`_dependency_install_command` 根据项目文件和命令判断依赖安装需求，`_offline_dependency_skip` 明确返回未执行测试的原因。Demo fixture 的设计和基础镜像能力因此会影响可运行性。

生产升级可以考虑预构建镜像、受控依赖缓存和独立依赖准备阶段；这些需要实际实现和验收，不能只关闭禁网来绕过问题。

#### 可能追问

为什么不自动联网安装？怎么固定依赖版本？跳过后最终结果怎样展示？

#### 容易答错的点

说禁网容器能自动下载任意依赖，或把依赖缺失算作补丁验证成功。

### 35. 问题：如何防止读文件越界和 symlink 泄漏？

#### 30 秒回答

文件访问必须以任务 workspace 为边界，检查路径解析结果，并限制符号链接。索引和工作区复制也需要避免把仓库链接指向的宿主文件带入系统。

#### 深挖回答

当前 runner 的读取逻辑检查路径及 symlink，工作区复制忽略符号链接；索引 staging 复制保留链接本身，后续扫描跳过，避免 copytree 提前解引用外部文件。

读取边界与补丁、容器挂载边界要分别评估。某个 ReadFile 测试通过，不能被扩大为整个执行系统不存在路径攻击风险。

#### 可能追问

路径中包含 ../ 怎么办？目录级 symlink 呢？检查后文件被替换属于什么问题？

#### 容易答错的点

只检查字符串前缀就声称安全，或用读取安全证明所有文件操作安全。

### 36. 问题：测试通过是否可能只是模型修改了测试？

#### 30 秒回答

可能，所以测试通过的证明范围必须说清楚。当前成功规则检查执行证据，不能仅凭它推导补丁没有削弱测试或改写验证入口。

#### 深挖回答

当前本地补丁路径经 AgentTools 进入 `git apply`，不能把动作 Schema、命令白名单或临时工作区解释为“全面禁止改测试文件”。补丁和测试脚本都应作为审查对象。

若要建立更强的修复评测，可以使用不可由 Agent 修改的外部测试、独立验证 checkout 和测试配置保护规则。这是升级设计，不能说当前已经全面实现。

#### 可能追问

怎样防止把断言删掉？如何验证新文件和测试配置的变更？隐藏测试足够吗？

#### 容易答错的点

把命令白名单误解为测试内容不可改，或声称 verified_success 等于不存在测试投机。

## G. 持久化、Checkpoint 与恢复

### 37. 问题：为什么修复任务通过 RQ 异步执行？

#### 30 秒回答

修复包含模型调用、代码调查和沙箱测试，耗时较长。RQ 让 API 提交任务后返回稳定 Run ID，Worker 独立执行，用户可以持续查看或稍后恢复查看结果。

#### 深挖回答

Run 先写数据库，队列只传 ID，Worker 使用新的数据库 Session 读取任务和身份上下文。每个生命周期阶段独立提交，整个修复不是一个长数据库事务。

队列解决调度，checkpoint 解决执行状态恢复，终态检查减少完成任务的重跑。队列自身不提供跨数据库的提交原子性或外部副作用的 exactly-once 保证。

#### 可能追问

为什么暂时不用 Celery？入队重复怎么办？数据库有 Run 但队列没任务怎么恢复？

#### 容易答错的点

说异步队列天然解决任务丢失、重复提交和所有故障恢复。

### 38. 问题：为什么使用 LangGraph，而不是简单 while 循环？

#### 30 秒回答

当前流程包含调查循环、补丁重试、验证分支和 MCP 暂停恢复，显式状态图更便于表达节点边界与恢复位置。简单流程也可以用 while，选型价值取决于是否需要这些状态语义。

#### 深挖回答

`graph.py` 把路由与节点职责分开，`FixAgentState` 承载证据、动作历史、补丁和测试结果。业务授权与验证逻辑仍在执行器和纯判定模块中，框架不自动提供这些保证。

图越复杂，状态兼容和 checkpoint 演进成本也越高。项目应围绕当前修复闭环解释必要节点，而不是为了展示框架增加角色。

#### 可能追问

哪些节点可以是纯函数？状态字段怎么演进？不使用 LangGraph 能否实现同样功能？

#### 容易答错的点

说 LangGraph 自动保证正确性、幂等或安全，或者把多节点等同于 Multi-Agent。

### 39. 问题：Checkpoint 保存什么？和 Timeline 有什么区别？

#### 30 秒回答

Checkpoint 保存机器继续执行所需的状态、channel 数据和 pending writes；Timeline 保存面向用户的动作与结果记录。前者用于恢复图，后者用于解释和审查过程。

#### 深挖回答

`SQLAlchemyCheckpointSaver` 将 `run_id` 用作 LangGraph `thread_id`，通过独立 checkpoint、blob、write 模型持久化。数据库表由 Alembic 管理。

`AgentStepService` 保存脱敏后的公开轨迹，并按配置处理受限敏感载荷。不能假设 checkpoint 自动拥有与公开 Timeline 完全相同的脱敏和保留策略，也不能用一份 UI 日志重建全部执行状态。

#### 可能追问

为什么只保存最终结果不够？pending writes 有什么作用？Checkpoint 会包含敏感源码吗？

#### 容易答错的点

把 Timeline 称为模型隐藏思维链，或声称机器恢复状态与展示日志是同一份数据。

### 40. 问题：Worker 在补丁应用之后退出，怎么恢复？

#### 30 秒回答

新执行会创建新的临时工作区，读取同一 Run 的 checkpoint。如果下一节点依赖已应用补丁，且保存状态证明补丁曾应用成功，就先重新应用保存的 patch，再从未完成节点继续。

#### 深挖回答

`_invoke_fix_graph` 读取 graph snapshot，有 pending 节点时调用 `_rehydrate_checkpoint_workspace`，然后使用 `graph.invoke(None, config)` 继续。已完成 checkpoint 可以直接恢复终态，恢复动作会进入 Timeline。

Checkpoint 保存的是逻辑状态，不是磁盘快照。恢复还依赖索引仓库基线、补丁可应用性和外部环境，不能承诺在任意仓库版本变化后都等价重放。

#### 可能追问

为什么不对所有恢复节点都重放补丁？源码已经更新怎么办？重放失败如何处理？

#### 容易答错的点

说 checkpoint 自动保存并恢复全部文件，或保证所有已发生副作用只执行一次。

### 41. 问题：RQ 配了重试，是不是任何失败都会自动恢复？

#### 30 秒回答

不是。队列重试只覆盖符合其失败机制的 job，服务已经捕获并保存为终态的错误，不会因为配置了 Retry 就自动重新执行整个修复。

#### 深挖回答

普通 Agent job 配置最多三次重试，间隔为 5、30、120 秒；`run_fix` 会跳过已有终态，并捕获部分执行异常写成 `infra_error`。因此必须区分 Worker 中断、可恢复 checkpoint 与被业务层结束的 Run。

Checkpoint 降低重启后从头运行的成本，但不能消除节点动作与 checkpoint 提交之间的窗口。每种副作用仍需要自己的恢复和幂等规则。

#### 可能追问

模型调用抛异常会重试吗？终态 Run 如何重新尝试？为什么不能重试所有错误？

#### 容易答错的点

照背“三次退避重试”就声称所有异常都会自动续跑。

### 42. 问题：为什么 MCP 远程执行还需要单独的 Ledger？

#### 30 秒回答

Graph checkpoint 记录本地流程位置，但远程写操作可能已经成功而响应丢失。Execution Ledger 记录逻辑调用身份、参数、执行租约和结果，帮助区分已完成、明确失败与结果未知。

#### 深挖回答

Ledger 使用稳定幂等键和状态流转；已知终态可以复用保存结果。远端未提供幂等契约时，Worker 失联后的调用可能进入 unknown，Agent 等待对账，不应直接重放写操作。

metadata 模式需要远端真正持久化同 key 去重结果。仅在请求里携带一个 key 不构成 exactly-once；超时和租约过期也要按各自恢复规则处理。

#### 可能追问

租约过期是否证明远端没执行？用户再次批准会重复写吗？本地幂等键能约束第三方吗？

#### 容易答错的点

把 checkpoint 当作分布式事务，或把 timeout 直接视为没有副作用。

## H. 前端展示、权限与审计

### 43. 问题：为什么用 SSE 展示任务轨迹？

#### 30 秒回答

修复执行在 Worker 中进行，浏览器主要接收进度与结果，SSE 可以表达这类单向更新。轨迹来源于持久化 AgentStep，重新连接能够重新读取已保存过程。

#### 深挖回答

`/runs/{run_id}/trace` 验证 Run 归属后返回事件流；前端在重连和展示时依据事件 ID 处理重复。读取 Run 也能取得持久化步骤，连接本身不是唯一数据来源。

这不同于代码 Chat 的 token 流。SSE 是传输方式，任务恢复来自数据库与 checkpoint，不能说 SSE 自动赋予任务恢复能力。

#### 可能追问

断线重连会不会重复显示事件？为什么不用 WebSocket？关闭浏览器是否会停止 Worker？

#### 容易答错的点

把网络连接寿命等同于后台任务寿命，或说 SSE 自动保证 exactly-once 交付。

### 44. 问题：Timeline 展示的是模型思维链吗？

#### 30 秒回答

它展示结构化计划说明、工具请求、观察、规则拒绝、测试结果和状态变化，用来解释发生了什么。它不等同于模型隐藏推理，也不证明模型真正采用了某种内部思考过程。

#### 深挖回答

Agent 的 hypothesis、rationale 属于显式输出字段；工具执行结果和验证证据来自执行层。`AgentStepService` 对调用与结果分别记录，Worker 在中间退出时也不会制造一个成功结果。

面试演示应以“请求了哪个工具、得到什么证据、测试发生什么变化”为主，避免把可见说明当成未经验证的事实。

#### 可能追问

模型说明与工具结果矛盾时信谁？为什么要分开记录 call 和 result？

#### 容易答错的点

把可解释轨迹说成完整暴露模型内部思考，或认为说明文字可替代原始测试证据。

### 45. 问题：首页 Demo 回放和真实任务有什么区别？

#### 30 秒回答

首页是基于内置 fixture 合约制作的可暂停流程回放，用于快速解释产品；真实任务则调用模型和沙箱，并从持久化 trace 展示实际执行结果。两者证据价值不同。

#### 深挖回答

`make demo` 导入确定性 Git fixture，建立 benchmark 并创建真实模型修复 Run，明确拒绝 mock LLM。购物车示例有两个相关修复点，适合观察目标与回归验证，但不强行编排第一轮失败。

回放可以证明界面表达了什么，真实 Run 可以证明这一次执行了什么，benchmark 才用于多个固定样例的统计。不能互相冒充。

#### 可能追问

现场没有模型凭据还能证明什么？怎么给面试官看真实证据？如果第一轮就修好怎么办？

#### 容易答错的点

把预制动画当作真实模型运行记录，或把单个成功 Demo 说成成功率评测。

### 46. 问题：如何避免用户通过猜 Run ID 读取别人的代码？

#### 30 秒回答

权限检查在可信后端完成，Repository 与 AgentRun 按 owner_id 限定查询。受保护部署使用签名产品身份；本地模式明确是单用户，不把本地默认身份解释为多用户隔离。

#### 深挖回答

例如 `get_owned_run` 同时按 Run ID 和 owner_id 查找，不匹配时返回 404，减少泄漏资源是否存在的信息。trace 同样需要归属检查，不能只保护页面入口。

创建 Run 时也检查仓库归属。多仓库检索的 repo filter 限定查询范围，但用户是否有权使用这些 repo 仍由 API 授权决定，Qdrant filter 本身不是身份认证。

#### 可能追问

前端隐藏按钮够吗？用户自行传 owner_id 有效吗？跨仓库问答在哪里鉴权？

#### 容易答错的点

说 UUID 难猜就安全，或将当前保护机制扩大为已完成工业级多租户 SaaS。

### 47. 问题：为什么代理转发的用户身份要签名和防重放？

#### 30 秒回答

普通 role、user header 可以被伪造，后端需要验证它们来自可信代理。签名把身份与请求绑定，timestamp 限制有效时间，nonce 防止同一签名请求在有效期内重复使用。

#### 深挖回答

Evaluation 身份签名覆盖 method、path/query、timestamp、nonce、role、user 和 provider。nonce 支持内存或 Redis 单次消费，多实例需要共享存储才能跨实例识别重放；后端还按 principal 做 RBAC。

签名保证请求来源和完整性，不代替具体资源授权，也不应扩大声称签了未纳入的字段。CI service token 与浏览器身份走不同权限范围。

#### 可能追问

为什么时间戳不够？轮换密钥怎么兼容旧实例？CI token 能修改数据集吗？

#### 容易答错的点

信任客户端自报 admin，或认为一个有效签名自动授权所有操作。

### 48. 问题：执行轨迹里有源码、Token 和敏感输出，怎么处理？

#### 30 秒回答

公开 Timeline 在写入前做脱敏；需要保留的受限载荷按配置独立加密并设置保留期限，读取也有权限边界。可观测性不能以把所有原始输入公开为代价。

#### 深挖回答

`AgentStepService` 对 input/output 分类，公开字段保存脱敏投影；受限密文绑定 Run、Step 和输入输出方向，到期可清除。工具异常也需要转换为适合公开的错误信息。

这套机制不等于整个系统所有存储和异常出口都已经完成同等级治理。Checkpoint、索引源码和外部服务结果要分别检查；KMS/SIEM 的真实部署状态也以 qualification 证据为准。

#### 可能追问

没有可用加密配置时会回退存明文吗？清理公开日志是否同时删除 checkpoint？

#### 容易答错的点

把日志脱敏描述为绝对防泄漏，或把本地加密测试当成生产 KMS 验收。

## I. Evaluation、指标与 CI Gate

### 49. 问题：怎么评价代码检索是否有效？

#### 30 秒回答

用带预期文件和代码位置的固定问题集，观察 Recall@K、MRR、nDCG、文件命中、行范围重合、Citation Precision 与延迟。它们分别衡量召回、排序、定位和使用成本。

#### 深挖回答

`EvaluationService` 逐 case 保存结果与失败类别，再聚合指标。Recall 关注相关目标是否被召回，MRR 关注首个相关结果位置；不同定位粒度的指标能揭示“找对文件但找错代码”的问题。

比较前需要固定数据集、仓库版本、Top K 和检索配置。这里测的是检索链路，不能直接把数值称为问答事实正确率或修复成功率。

#### 可能追问

Recall 高但引用精度低说明什么？为什么还需要行级指标？标注怎么做？

#### 容易答错的点

把向量 score 当准确率，或只用延迟证明代码理解质量。

### 50. 问题：Verified Fix@1 和 Final Verified Fix Rate 怎么计算？

#### 30 秒回答

当前 Fix@1 统计在一次补丁尝试内达到 verified_success 的 case；最终 Verified Fix Rate 统计允许迭代后达到该终态的 case。分母是参与统计的 case 总数，不能只保留成功复现的样本来美化结果。

#### 深挖回答

`_fix_metrics` 按 agent_status 和 iterations 计算，保留 `fix_success_rate` 作为最终 verified rate 的兼容别名。它还统计基线复现率、补丁应用率、回归表现、工具调用和 token 等。

Evaluation 的 passed 可能表达“结果符合该 case 的预期”，不等于 Agent 真的修复成功。例如预期失败的负例正确失败，可以符合预期，但不计入 verified success。

#### 可能追问

基础设施错误是否影响分母？预期失败样例为什么能 passed？空数据集的数值怎么解释？

#### 容易答错的点

把 expectation match rate 当修复成功率，或把测试跳过样例算作修复成功。

### 51. 问题：目前公开的 93.33% 能证明什么？

#### 30 秒回答

它是已提交本地 retrieval artifact 中，30 个 case 的 hybrid Recall@5。该记录明确标为 engineering_smoke_only，使用 deterministic mock embedding，不能被描述为真实 embedding 模型或修复 Agent 的效果。

#### 深挖回答

历史 artifact 记录的运行时间为 2026-08-02，hybrid MRR 为 0.6956，p95 延迟为 17.5 ms，同时注明 worktree dirty。vector-only 在共享 0.72 阈值下没有返回有效结果，因此不能据此断言真实向量检索没有价值。

这证明 benchmark 与消融执行链路产生了测量结果。真实模型 Fix@1、反思后的成功率和 planner 消融结果在已提交结果说明中仍是 not_run。

#### 可能追问

为什么 mock 也能有高 Recall？dirty worktree 对复现有什么影响？是否隐藏了差的实验结果？

#### 容易答错的点

把 93.33% 写成修复成功率，或把历史 smoke 数据当成本轮重新执行的结果。

### 52. 问题：如何证明 Hybrid、Rerank 和 Reflect 各自有用？

#### 30 秒回答

需要控制变量的消融实验：检索比较 vector-only、hybrid、hybrid 加 rerank/context；修复比较单次尝试与反思，以及固定 planner 和自适应 planner。不能只拿一个成功案例推断因果。

#### 深挖回答

仓库的 ablations 配置与 benchmark matrix runner 定义了这些变体，并检查部署配置是否匹配变体名称。对照还应保持 fixture commit、问题集、模型和预算一致。

如果一个变体同时加入 rerank 和 context expansion，它只能说明这组变化的整体结果，不能独立归因给某一个机制。真实模型还需要重复运行，观察随机性和失败分布。

#### 可能追问

怎么避免 token 预算不同造成不公平？是否要固定 seed？统计提升有多稳定？

#### 容易答错的点

把两个同时变化的组件分别宣称为提升来源，或把待运行矩阵说成已完成实验。

### 53. 问题：为什么数据集要保存 Snapshot？

#### 30 秒回答

可编辑数据集会变化，历史 Run 必须绑定当时的 case 内容，才能解释过去结果并公平比较。Snapshot 保留评测输入版本，避免同名数据集已经换题却仍直接比较分数。

#### 深挖回答

Evaluation Run 保存 dataset_snapshot_id、版本与配置快照，artifact 进一步提供代码、Prompt 和 fixture 的溯源信息。比较和 gate 会检查快照、任务类型、Top K 等相关条件。

固定输入不等于模型输出完全可复现，也不意味着每份 artifact 都来自干净提交。缺失信息和 dirty 状态必须保留，不能事后补写成更强证据。

#### 可能追问

只保存数据集名称为什么不够？历史记录没有快照怎么办？模型服务升级怎么追踪？

#### 容易答错的点

认为固定 Prompt 就能完全复现，或把运行时快照当成所有外部依赖都已冻结。

### 54. 问题：CI Evaluation Gate 如何防止质量退化？

#### 30 秒回答

CI 创建候选评测 Run，与指定 baseline 比较，按策略检查质量和可比性，并导出可追溯 artifact。门禁结论必须来自实际评测结果，不能仅根据构建成功判断 Agent 没有退化。

#### 深挖回答

仓库脚本支持生成候选、等待完成、检查 gate，并输出 JSON、Markdown 和历史趋势。脚本区分通过、失败以及不确定或 API 错误，结果文件应在失败时也保留。

已有 workflow 定义说明流程可配置，不等于已经有成功远程 CI receipt。面试时需要指出 baseline、数据集、策略和运行证据分别在哪里。

#### 可能追问

没有 baseline 怎么办？不可比运行应该放行吗？如何处理模型波动导致的偶发门禁失败？

#### 容易答错的点

把 YAML 文件存在说成持续评测已在线稳定运行，或在网络失败时伪造 gate passed。

## J. 设计取舍与高压追问

### 55. 问题：为什么没有把每个节点做成独立 Agent？

#### 30 秒回答

当前核心任务是一条受控修复流程，角色拆分不一定带来更好结果。复现、授权、验证和持久化适合确定性代码，动态调查由 planner 负责即可形成清楚边界。

#### 深挖回答

多个 Service、多个模型调用和多个图节点，都不自动构成多个自治 Agent。增加独立角色还会增加上下文传递、冲突处理、预算分配和评测复杂度。

若要讨论多 Agent，应先找到可独立完成且能合并验证的子任务，再用相同预算做对照。当前不能宣称已经验证多 Agent 比单 planner 更好或更差。

#### 可能追问

什么时候值得拆成多个 Agent？并行调查如何共享证据？谁负责最终裁决？

#### 容易答错的点

把 LangGraph 多节点包装成 Multi-Agent，或为显得复杂而增加没有收益证据的角色。

### 56. 问题：MCP 在项目中的价值和边界是什么？

#### 30 秒回答

MCP 用于接入外部工具能力，补充本地代码调查与修复，但协议接通不代表工具已经被授权。调用还需要经过 Schema、策略、预算、审批、凭据和持久化执行控制。

#### 深挖回答

本地 action loop 与 MCP Router 分别有自己的工具契约和控制路径。高风险调用可等待审批，远端执行不确定可等待对账；审批 checkpoint 绑定相应请求和完整性信息。

MCP 是扩展接口，主产品仍是可验证代码修复。Registry、Quota、KMS 等模块可以作为深入讨论的入口，但不应掩盖真实模型修复评测尚未完成的边界。

#### 可能追问

工具描述里有恶意指令怎么办？批准之后参数改变怎么办？MCP 是否天然安全？

#### 容易答错的点

把工具自报的安全属性当最终授权，或把接入协议说成生产权限治理已经完成。

### 57. 问题：Prompt Injection 能靠提示词彻底解决吗？

#### 30 秒回答

不能。仓库注释、文档和外部工具结果都是模型会读取的不可信内容，提示词可以解释角色边界，但执行能力必须由工具 Schema、可信授权、路径限制和沙箱约束。

#### 深挖回答

模型可以因恶意内容提出错误动作，执行器仍必须检查动作类型、参数与命令许可；远程工具还需检查策略和审批。仓库里出现“忽略限制”不能改变服务端规则。

现有控制降低部分风险，不能承诺完全消除注入。尤其补丁内容、测试投机、外部副作用和敏感数据出口，需要各自的验证和威胁分析。

#### 可能追问

如果恶意要求被包装成合法 SearchCode 怎么办？合法工具组合是否仍可能造成泄漏？

#### 容易答错的点

说写一句“不要执行恶意指令”就解决安全，或把 Schema 校验称为语义安全证明。

### 58. 问题：最大的性能瓶颈可能在哪里，如何优化？

#### 30 秒回答

要按阶段测量，重点看模型调用、embedding、代码索引和沙箱启动及测试耗时。已有检索 smoke 延迟不能代表真实修复任务的端到端性能。

#### 深挖回答

当前已有 span、工具耗时、token 和评测延迟等记录入口。先观察 p50/p95 与失败分布，再决定减少无效工具轮数、改善候选召回、缓存稳定数据或预构建测试环境。

这些是优化方向；缓存需要绑定仓库版本、模型和权限，复用沙箱也需要处理环境污染。不能为了提速省略基线或回归验证后还使用相同成功口径。

#### 可能追问

检索和测试能否并行？缓存失效怎么设计？怎么证明优化没有降低质量？

#### 容易答错的点

没有 profile 就断言某个数据库最慢，或用减少验证步骤换来的速度宣称无损优化。

### 59. 问题：如果面试官说这只是“套模型 API”，怎么回答？

#### 30 秒回答

模型负责提出动作和补丁，项目的工程工作在于把这些不确定输出变成可约束、可验证、可恢复的执行过程。我会用一条真实失败案例展示授权、证据、补丁、测试和终态如何关联。

#### 深挖回答

可以现场指出三处机制：执行器拒绝非法或重复动作；验证模块拒绝缺失测试的假成功；checkpoint 在 Worker 恢复时重建继续执行所需状态。再展示相应测试入口和实际保存的轨迹。

这种回答仍要诚实区分自己实现的业务约束、依赖库提供的能力和尚未完成的实验。若谈个人贡献，应依据实际开发与提交记录，不把整个仓库默认说成全部独立完成。

#### 可能追问

去掉模型后系统还剩什么？最难处理的故障是什么？哪些部分是你独立设计的？

#### 容易答错的点

靠堆技术名词回避问题，或编造个人贡献、历史故障和成功率。

### 60. 问题：如果继续投入，优先改进哪三件事？

#### 30 秒回答

我会优先完成真实模型固定基准评测、增强独立验证与测试完整性，再补齐恢复基线和执行环境的可靠性证据。顺序围绕能否证明修得对、验证是否可信、故障后是否一致展开。

#### 深挖回答

第一，固定 fixture、模型、Prompt 与预算，发布真实 Fix@1、最终成功率和失败分类。第二，让验证用例与 Agent 可编辑工作区有更清楚的独立边界，评估测试被削弱和配置被改写的情况。第三，核实仓库版本绑定、节点副作用窗口、并发任务与实际沙箱故障恢复。

若目标变成对外多用户托管服务，租户隔离、凭据治理、仓库导入 egress 和真实 runtime qualification 是上线前置工作。现有 Firecracker/Kata 工件与 KMS/SIEM 演练脚本不能替代真实部署验收；这些是改进方向，不是本次已交付能力。

#### 可能追问

为什么不先加更多语言和 Agent？如何决定上线门槛？怎样把三项改进变成可验收任务？

#### 容易答错的点

把尚未实施的方案说成现有能力，或用功能数量代替正确性与证据质量。
